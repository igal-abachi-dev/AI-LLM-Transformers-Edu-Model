Environment: Windows 11, Python 3.12.10, PyTorch 2.13.0+cu130, NVIDIA GeForce RTX 2070 SUPER
(Turing, compute capability 7.5, 8GB VRAM), driver 591.86. Date: 2026-08-21. Git commit

has had; every prior evidence file was CPU-only.

## Prerequisite fixes discovered during this pass

- **`KVCache` CUDA device-index bug** (`src/minifrontier/cache.py`): a bare `torch.device("cuda")`
  (`index=None`) compares unequal to a real tensor's `torch.device("cuda", 0)` in PyTorch. Every
  documented `--device cuda` invocation with a lazily-dtyped cache (the recommended, default pattern)
  failed on the first cached forward pass with `ValueError: cache device does not match model
  inputs`. Invisible to CPU-only CI, since CPU devices have no index ambiguity. Fixed by resolving
  the CUDA index at `LayerKVCache.allocate` time. Regression-covered by
  `test_cuda_bfloat16_full_and_cached_logits_match_within_declared_tolerance`.
- **`train/pretrain.py` resumed-run throughput inflation**: `tokens_per_second` divided the
  checkpoint's cumulative `consumed_target_tokens` by only the current process's wall time. After a
  resume, this silently counted tokens processed by an earlier, separate process against the new
  process's clock — observed as 10,388 tok/s (wrong) vs a corrected 6,728 tok/s (right) on the
  identical resumed workload. Fixed by tracking tokens consumed since this process's own start.
- **Missing `.github/workflows/ci.yml`**: absent from the working tree and git history despite
  MF-002/MF-068 and prior evidence claiming it existed and was green. Recreated; verified
  `scripts/build_source_archive.py` succeeds again (see MF-002 status note in `tasks/backlog.md`).
- Added `../train/pretrain.py` to the `--help` CLI smoke parametrize list in `tests/test_clis.py` —
  it was the only script under `train/`/`scripts/` missing from that coverage.
- Added `data/` to `.gitignore` (mirroring the existing `artifacts/*` / `!artifacts/.gitignore`
  pattern) so real corpora/tokenizer/shard artifacts produced below stay untracked.

## MF-046 / MF-049 — new CUDA test coverage

Three new tests in `tests/test_training.py`, guarded by `@pytest.mark.skipif(not
torch.cuda.is_available(), ...)`, tolerances declared before running:

- `test_cuda_bfloat16_full_and_cached_logits_match_within_declared_tolerance` — BF16 full-vs-cached
  logits within `atol=5e-2` (BF16's ~3-decimal-digit mantissa), exact argmax agreement, and confirms
  the cache adopts BF16 lazily from the autocast projections rather than the embedding dtype. PASSES.
- `test_cuda_gradient_accumulation_matches_unsplit_batch` — matches the CPU test's structure on CUDA,
  `atol=1e-5` (looser than CPU's `1e-6`, since cuBLAS/cuDNN reductions are not bit-identical to CPU).
  PASSES.
- `test_cuda_activation_checkpointing_matches_loss_and_gradients` — same, `atol=1e-5`. PASSES.

## MF-050 — profiling matrix

Full results and findings: `reports/mf050-rtx2070s-profile-matrix.md`, raw records
`reports/mf050-*.json`. Highlights: this GPU has no native BF16 tensor cores (FP32 measured faster
than BF16); `torch.compile` explicitly declines native BF16 compilation and gives no steady-state
benefit; an 8K-context 150M-modern benchmark exceeded the 8GB physical VRAM (peak ~10.9GB allocated)
and silently fell back to slow system-memory paging rather than crashing, while the ring-cache byte
saving itself measured correctly (~3.4x at that context length).

## MF-049 — checkpointing benchmark

Full results: `reports/mf049-rtx2070s-checkpointing-benchmark.md`. At batch_size=1 (fits either way):
checkpointing trades ~22% throughput for ~28% VRAM. At batch_size=4: eager exceeds this 8GB card's
VRAM and never completed 60 updates in 400s+ (thrashing); checkpointing completed cleanly in 105.7s —
the real value on this hardware is enabling batch sizes eager cannot practically run at all.
