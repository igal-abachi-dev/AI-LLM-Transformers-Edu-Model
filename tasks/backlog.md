# MiniFrontier V1 implementation backlog

This backlog freezes the build described in [`plan.md`](../plan.md): one raw-PyTorch decoder-only model, Edu and Modern presets, a 16K byte-level BPE tokenizer, from-scratch training, inference, evaluation, FIM, and small SFT. It deliberately excludes DeltaNet, MLA, MoE, RL, agents/tools, distributed training, custom kernels, and long-context production serving.

## Conventions

- **Priority:** P0 blocks the next milestone; P1 is required for V1; P2 is optional after V1.
- **State:** `Planned` initially. Move only dependency-free work to `Ready`.
- **Definition of done:** acceptance criteria pass, relevant tests are committed, documentation is updated, and no unrelated scope is added.
- **Evidence:** record exact commands, seed, config, environment, and metrics for training or benchmark tasks.
- **Hardware scheduling:** by user decision, CUDA/RTX execution evidence is collected after M10 implementation. CPU-verifiable code may proceed through M9, but tasks requiring trained 150M artifacts or GPU measurements remain open until those runs actually complete.

### MF-050 — Profile and tune the 24–32 GB GPU path

- **Priority / state:** P0 / Done
- **Depends on:** MF-037, MF-046, MF-047, MF-048, MF-049
- **Deliverable:** measured eager/SDPA/compile/checkpointing matrix for 50M and 150M plus a hardened single-stream inference path and long-context hybrid benchmark.
- **Acceptance:** generation computes only requested logit positions (`last-token` for ordinary prefill/decode) instead of materializing unused `[B,S,V]` logits, and output token storage avoids per-token whole-prefix concatenation; temperature is finite, top-k/top-p edge cases have hand-checked tests, filtering performs no redundant softmax, and non-finite model outputs fail diagnostically in an explicit debug/validation mode rather than being silently sanitized in the hot path. The full-history local cache remains the correctness reference; an optional bounded window/ring cache must track absolute RoPE positions, expose only initialized slots in chronological order, and match reference logits/argmax across wrap, chunk, reset, rollback, and mixed local/global layers. Single-token parity must cross at least two complete local-window wraps. - **Decisive hybrid test (2026-09-04, real GPU evidence, confirms the recommendation):** the user asked whether combining every real Muon speed win (FP32 Newton-Schulz + `ns_steps=3`) at Muon's best known LR (1e-2) could close the gap. ### MF-084 — Chunked cross-entropy (plus near-free z-loss) to reduce logits memory pressure

- **Priority / state:** P0 / Done
- **Depends on:** MF-041
- **Deliverable:** compute `lm_head` projection and cross-entropy loss over sequence-length chunks and sum, instead of materializing the full `[B, S, vocab_size]` logits (and their FP32-upcast gradient) in one piece — a real, measurable memory reduction at this project's vocabulary size on an 8GB card. Since the chunk loop already computes each chunk's log-sum-exp explicitly, fold in z-loss (PaLM-style `λ·log²(Σexp z)` logit-magnitude penalty) as a near-free addition — no second pass over the logits — rather than treating it as a separate ablation item.
- **Acceptance:** chunked and unchunked loss agree exactly (or within documented FP32 tolerance) on the same batch; peak VRAM at a fixed batch size/context measurably drops (or, equivalently, a larger batch size/context becomes reachable at the same VRAM ceiling), measured for real on this hardware, not estimated; z-loss is off by default (`TrainingConfig` weight, defaulting to 0.0), and its own contribution to the loss stays out of the logged/reported primary loss, matching the MTP auxiliary-loss precedent in `training.py`.
- **Status note:** proposed by external code review, correctly identifying that `next_token_loss_stats`'s full `[B, S, V]` logits plus their FP32-autocast-upcast gradient is a disproportionate memory cost for a small model. The review's other suggestion, "Cut Cross-Entropy" (arXiv:2411.09009), is **not** adopted as stated — it requires custom Triton kernels, which `AGENTS.md`'s frozen V1 scope explicitly excludes ("Do not add... custom CUDA/Triton kernels... in V1"). **Reprioritized to P0, ahead of [[MF-087]], 2026-09-06**: doubling the tokenizer's vocabulary directly doubles this exact memory cost, on hardware already shown to hit VRAM-thrashing at modest headroom margins (`batch_size=4` caused 9.25GB thrashing at the *current* 16k vocab — MF-065's own status note).
  - **Implementation, per a second review round that sharpened the design**: a naive per-chunk `torch.utils.checkpoint` approach was rejected — it recomputes the `lm_head` projection during backward, costing a verified ~5.6% of forward+backward compute (~11 hours over a real 8-day 3B-token run) for no reason. Instead, `src/minifrontier/loss.py` adds `_ChunkedCrossEntropy`, a custom `torch.autograd.Function` whose `forward` computes each chunk's loss *and* its closed-form gradient (`dL/dlogits = softmax(logits) - one_hot(target)`) together, discarding that chunk's `[C, vocab_size]` logits immediately and accumulating only `hidden`/`weight`-shaped gradients; `backward` then does no recomputation at all, just returns what `forward` already built — so the rest of the model's backward pass still runs exactly once, not once per chunk (a plain per-chunk `.backward()` loop without a custom Function would re-walk the entire transformer's graph on every chunk, which was seriously considered and rejected during implementation for being far more expensive than either alternative). `chunked_next_token_loss_stats(hidden_states, weight, tokens, ...)` wraps it with the same shift/mask/offset contract as `next_token_loss_stats`, plus `z_loss_weight`. `MiniFrontier.forward` gained `skip_logits: bool` to skip the `lm_head` call entirely when the caller is about to score `hidden_states` itself in chunks. `TrainingConfig` gained `loss_chunk_size: int | None = None` (opt-in; `None` preserves the exact original full-materialization path, matching the manual-attention-kept-alongside-SDPA/Flex precedent of never deleting a simpler reference path) and `z_loss_weight: float = 0.0` (requires `loss_chunk_size` to be set).
  - **Correctness verification**: `torch.autograd.gradcheck` (finite-difference vs. analytical gradient — the definitive check for a hand-derived backward, not just agreement with another implementation that could share the same mistake) passes for both the main loss and z-loss terms; chunked and unchunked loss_sum/count match within 1e-9 across offset∈{1,2}, uneven/exact/single chunk sizes, `loss_mask`, and scattered `ignore_index` targets; a full `train_updates` run from identical starting weights produces bit-for-bit identical final weights whether `loss_chunk_size` is set or not; a tied-embeddings model's shared `token_embedding.weight`/`lm_head.weight` correctly accumulates the chunked path's gradient. 12 new tests across `test_loss.py`/`test_model.py`/`test_training.py`; full fast suite 225 passed (up from 215), `ruff check`/`format --check` clean.
  - **Real measured result** (`labs/09_chunked_vs_fused_cross_entropy.py`, RTX 2070 Super, `batch_tokens=2048, d_model=768, vocab_size=32768, chunk_size=512`): peak allocated memory dropped from 1,189.4MB to 646.2MB, a real **1.8x reduction** (smaller than the ~4x element-count arithmetic suggests, due to allocator overhead/fragmentation and the reference path's own extra autograd-graph buffers — reported as measured, not reconciled to the estimate). This is the same lab the reviewer suggested as a teaching artifact showing the memory arithmetic (naive vs. chunked, no Triton needed); it doubles as this task's own real-hardware evidence.
  - z-loss folded in per the reviewer's own follow-up ("zero wall-clock cost, well-attested, can't plausibly hurt → adopt without ablation" — see [[MF-081]]'s revised scope).
  - **Follow-up (2026-09-07): real gap found — none of this was reachable from real training.** A second code-review round correctly found that `train/pretrain.py` and `train/sft.py` built `TrainingConfig` from CLI args without `loss_chunk_size`/`z_loss_weight` among them (confirmed: grepping the whole repo outside `src/`/`tests/` found zero references to either field before this fix), so the real 3B-token run at 32k vocab would have silently taken the unfused path regardless — precisely the OOM risk this task exists to prevent. `mtp_extra_heads`/`mtp_loss_weight` had the identical gap. Fixed: `--loss-chunk-size`/`--z-loss-weight` added to both `train/pretrain.py` and `train/sft.py`; `--mtp-extra-heads`/`--mtp-loss-weight` added to `train/pretrain.py` (constructs `MTPHeads`, adds its params to the optimizer, passes `mtp_heads=` to `train_updates`) with a new guard rejecting `--resume` combined with `--mtp-extra-heads > 0` (MTP head weights are not part of the saved checkpoint, so resuming would silently reinitialize them — documented, not silently broken). Four new functional tests in `tests/test_pretrain_cli.py` exercise real training runs through the new flags, not just `--help`.
  - **Follow-up (2026-09-07): three real memory findings in `_ChunkedCrossEntropy`, all fixed.** (1) `grad_hidden_z`/`grad_weight_z` were allocated unconditionally regardless of `z_loss_weight` — at 32k vocab, `grad_weight_z` alone is ~100MB held from forward through backward for nothing when z-loss is off (the default); now allocated only when `z_loss_weight` is truthy. (2) The per-chunk loop held three `[chunk_size, vocab_size]`-shaped tensors simultaneously (`logits_chunk`, `probabilities`, and a `.clone()` of `probabilities`) — roughly 3x the necessary peak; now reduced to ~1x by computing z-loss's gradient from the untouched softmax first, then mutating `probabilities` in place for the main gradient instead of cloning it, and freeing `logits_chunk` as soon as `probabilities` exists. ### MF-089 — Fix FlexAttention block-mask cache sharing a mask across inference/training contexts

- **Priority / state:** P0 / Done
- **Depends on:** MF-080 (the LRU bound added to this same cache)
- **Deliverable:** `_flex_block_mask`'s shared `_BLOCK_MASK_CACHE` must never let a `BlockMask` built while `torch.inference_mode()` is active be reused later inside an ordinary autograd-tracked (training) forward pass.
- **Acceptance:** a `BlockMask` constructed under `torch.inference_mode()` is never written into the shared cache (reading a mask already in the cache while inside `inference_mode()` remains fine and unaffected — only writing a tainted one in was the hazard); a real end-to-end reproduction (inference-mode forward pass, then a same-shape training forward+backward in the same process) succeeds without raising.
- **Status note:** found for real, not via code review, while running [[MF-087]]'s tokenizer comparison: `scripts/compare_tokenizers.py`'s new checkpoint-reuse path calls `evaluate_token_batches` (`@torch.inference_mode()`) for the 16k arm *before* training the 32k arm in the same process. Both arms use the same `sequence_length`/`local_window`, so `_flex_block_mask`'s cache key matched, and the 32k arm's training reused a `BlockMask` object that had been built (and cached) under `inference_mode()` during the 16k arm's validation — crashing with `RuntimeError: Inference tensors cannot be saved for backward` deep inside FlexAttention's autograd op the moment training tried to backpropagate through it. This was a real, previously-latent bug in `src/minifrontier/attention.py` predating this session's own MF-080 LRU-bound fix to the same cache (the bug is about *what* gets cached, not the bound itself) — every prior script this session only ever went train-then-validate in that order within one process, which never triggers it (a plain, non-inference-tainted cached mask is safe to read from within a later `inference_mode()` call; the danger is strictly the other direction). Fixed: `_flex_block_mask` now skips the cache *write* (not the read) whenever `torch.is_inference_mode_enabled()` is true, so a tainted mask is never shared regardless of call order. Verified as a real regression, not a coincidence: temporarily reverted the fix and confirmed both new tests fail with the exact reported error, then restored it and confirmed both pass. Two new tests in `tests/test_modern.py` — a CPU-safe cache-isolation check, and a CUDA-gated full reproduction of the real crash (FlexAttention does not support backward on CPU at all, unrelated to this bug, so the full scenario needs real CUDA hardware to exercise). Full suite passes (232 passed, up from 230), `ruff check`/`format --check` clean.
- **Follow-up (2026-09-07): reliability review requested and one more real (but not yet triggered) issue found and fixed.** After this crash, the user asked for a broader sweep of `src/minifrontier/` for the same class of bug (shared, unscoped state that behaves correctly in every tested call order but not all realistic ones). Swept for other module-level mutable caches, `functools.lru_cache`/memoization, mutable default arguments, global CUDA device/dtype pollution, and class-level mutable dataclass fields — `_BLOCK_MASK_CACHE` was confirmed the only instance of the caching hazard (the fix above already covers all four `torch.inference_mode()` call sites in the codebase, not just `evaluate_token_batches`); `generate()`'s inference path uses `@torch.no_grad()` (not `inference_mode()`) and allocates a fresh `KVCache` every call, so it has no analogous risk; `_compiled_flex_attention` caches a compiled function rather than a tensor and is unaffected (`torch.compile` re-guards on grad-mode changes), and is moot in practice anyway (off by default, confirmed non-functional on this hardware per [[MF-078]]). Not currently triggered (every real script in this project calls this once with one consistent `device`/`deterministic` value for its whole run), but the same "works in every tested order, not all realistic ones" shape as the bug above — a future script mixing a CPU-deterministic phase with a later CUDA phase in one process would inherit a stuck `True`, and PyTorch raises (rather than silently degrading) on any CUDA op lacking a deterministic implementation while that flag is on. ### MF-082 addendum: DeepSeek-V4's real attention-sink formula (2026-09-08)

Verified real (primary source, `arxiv.org/html/2606.19348v1`), and directly relevant to the "gpt-oss-style learned per-head sink logits" alternative [[MF-082]]'s own task description already named but did not choose (per-head *gated* attention was implemented and tested instead — see [[MF-082]]'s 2026-09-08 progress note). DeepSeek-V4's real mechanism, precisely: one learnable scalar `z'_h` per attention head, added as an extra `Exp(z'_h)` term in the softmax denominator alongside the real keys' scores — `s_{h,i,j} = Exp(z_{h,i,j}) / (sum_k Exp(z_{h,i,k}) + Exp(z'_h))` — letting a head's total attention weight sum to less than 1 (effectively attending to a learned "nothing" option) rather than always being forced to distribute exactly 100% of its probability mass across real tokens. This is a real, precisely-specified, frontier-validated version of the alternative this project did not build. Not a reason to revert the already-implemented, already-tested gated-attention fix without evidence — recorded so the sink-logits formula is available, precisely, if [[MF-082]]'s own real bounded test (once run) says gated attention underperforms and this alternative is worth trying instead.

### A future 1B-scale initiative (2026-09-10 feedback): recorded as context, not scoped, deferred like MF-098's distillation arc

External feedback proposed a concrete ~1B-parameter "ModernLM-1B" architecture (20 layers, d_model=2048, 16 Q/4 KV heads, head_dim=128, d_ff=5504, 64K-vocab) and separately described Qwen3.5-0.8B's real current architecture — verified real by the feedback's own citations (`Qwen/Qwen3.5-0.8B`'s config): 24 layers alternating 3 Gated DeltaNet layers then 1 full-GQA-attention layer, partial RoPE, output gating, a 248,320-token vocabulary, and an auxiliary MTP layer. The feedback's own conclusion is to build the simpler GQA+SwiGLU dense shape for a first 1B model, not clone Qwen3.5's DeltaNet hybrid — DeltaNet needs specialized `causal_conv1d`/FLA kernels or falls back to a much slower plain PyTorch path, which the feedback itself frames as a v2-or-later idea. This matches `AGENTS.md`'s own existing exclusions exactly (no DeltaNet/linear-attention hybrids, no MoE, no native multimodality) — no scope change indicated. The feedback also makes a real, checkable hardware argument: at `6 * params * tokens` FLOPs, a 1B-parameter/2T-token run (matching Gemma 3 1B's/OLMo 2 1B's own real published token budgets) is on the order of years even at this project's reference card's theoretical peak throughput, confirming this project's own repeated framing that the 2070 Super is a development/inference card, not a competitive-pretraining one. **A genuine 1B preset is not in this project's frozen V1 scope at all** (`AGENTS.md`: "350M and 500M are optional post-V1 scale checks" — no 1B) — recorded here as real, useful context for whenever that scope question is revisited, explicitly deferred alongside [[MF-098]]'s distillation/post-training arc and any distributed-training work, per the user's own explicit instruction to set both aside for now.
